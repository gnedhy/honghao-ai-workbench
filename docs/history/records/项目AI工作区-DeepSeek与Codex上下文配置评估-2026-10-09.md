## 结论

4,464 tokens 的自动压缩阈值不适合作为持续会话的常态配置。它来自 H05 累计运行预算及 UTF-8 请求大小预留的推导，不是 DeepSeek 或 Codex 的默认值。应先区分模型窗口、单次输出、请求字节限制和累计用量预算，再使用固定内核的模型压缩规则；不能只提高压缩阈值而保留不匹配的代理门禁。

不额外指定未经实测的 128K 窗口或 80% 阈值。来源明确的基线是保留实际 1M 模型窗口，取消 H05 自算的自动压缩覆盖，由固定内核按模型信息生成阈值。这个基线还不能作为现有部署已支持长上下文的结论。

## 实际模型与 API 合同

现役代理调用 `https://api.deepseek.com/responses`，模型 ID 是 `deepseek-flash`。本次使用现有接入账号只读查询 `/models`，与[模型查询文档](https://api-docs.deepseek.com/api/list-models/)及[模型说明](https://api-docs.deepseek.com/quick_start/pricing/)对照：

| 项目 | 核对结果 | 对 H05 的影响 |
| --- | --- | --- |
| 实际模型名称 | DeepSeek-V4.1-Flash | 不能沿用旧型号的窗口或输出限制 |
| 总上下文窗口 | 1,048,576 tokens | 输入和输出共用容量，不等于汉字数或 UTF-8 字节数 |
| 最大输出 | 393,216 tokens | API 能力上界，不能直接用作产品每次回复的预算 |
| 输入／输出 | 文本、图像输入；文本输出 | H05 当前仍只开放文本，模型能力不代表产品已启用 |
| 推理档位 | low、high、max；默认 high | 正文运行当前显式 low，短标题显式 none |

[Responses API](https://api-docs.deepseek.com/api/create-response/)定义 `max_output_tokens` 同时包含推理和可见正文。H05 显式设为 4,096，不能理解为可见正文独占 4,096。输入、推理、输出的用量分别按官方字段记录；实际返回的 usage 是计量依据。

[Chat Completions 文档](https://api-docs.deepseek.com/api/create-chat-completion/)列出未设置输出限额时的默认值：非思考 8K、思考 64K、max 档思考 128K。不能把 Chat Completions 的默认数值不加区分地套给当前 Responses 请求；当前服务已有显式输出值，不依赖这些默认值。是否扩大正文输出额度，应通过推理／正文占比和截断结果验收。

## 历史、压缩和缓存

[DeepSeek Responses 兼容指南](https://api-docs.deepseek.com/guides/responses_api/)明确 API 无服务端会话状态：不支持 `previous_response_id`、`conversation`、`store` 和 `context_management`，也不提供 OpenAI 的加密压缩内容协议。客户端必须发送当前有效历史，历史可以是 harness 保留的最近内容与压缩摘要。不能依赖服务器自动记住上一轮，也不能把 OpenAI 的服务端压缩配置直接转交 DeepSeek。

[DeepSeek 缓存说明](https://api-docs.deepseek.com/guides/kv_cache/)中的自动上下文缓存用于复用请求前缀，不能代替历史传递或摘要压缩；上下文占用与命中缓存的计费用量是不同事实。缓存命中应继续统计为模型输入，不应从窗口占用中扣掉。

[思考模式说明](https://api-docs.deepseek.com/guides/thinking_mode/)区分无工具与工具请求的推理历史规则；当前 H05 文本代理不公开工具。后续工具阶段应重新核对推理历史兼容性，不在本轮启用图像、文件、搜索或工具。

[并发及连接说明](https://api-docs.deepseek.com/quick_start/rate_limit/)列出的 Flash 账号并发上限为 2,500；这不是本服务的授权并发，也不是 Linux 进程数。H05 原并发、180 秒墙钟和连接超时保护继续独立存在，长上下文场景的耗时须实测。

## 固定 Codex 0.160.0 的真实规则

官方[配置参考](https://developers.openai.com/codex/config-reference/)区分模型窗口与自动压缩阈值；阈值未设置时使用模型默认。核对[固定版本 ModelInfo](https://github.com/openai/codex/blob/rust-v0.160.0/codex-rs/protocol/src/openai_models.rs)的实现，而非把最新文档或其它模型的数字移用于当前内核：

| 项目 | 当前模型目录／内核规则 | 计算值 |
| --- | --- | --- |
| 模型声明窗口 | 与实际 API 元数据一致 | 1,048,576 |
| 可用窗口 | 当前目录 effective_context_window_percent=95 | 996,147 |
| 目录自动压缩值 | auto_compact_token_limit=null | 使用内核默认 |
| 默认自动压缩阈值 | 模型声明窗口的 90%；显式覆盖也受该上界约束 | 943,718 |
| 换算为现有界面进度 | 默认阈值／可用窗口 | 约 94.74% |

所以 90% 是相对于声明窗口，94.74% 是相对于界面可用窗口；不能把两个分母混用。当前 996,147 的显示有明确来源。

[固定版本执行流程](https://github.com/openai/codex/blob/rust-v0.160.0/codex-rs/core/src/session/turn.rs)在开启后续推理前及执行中检查阈值；远端压缩不支持时走原生本地压缩任务，向模型请求摘要并持久保存替换后的有效上下文。[本地压缩实现](https://github.com/openai/codex/blob/rust-v0.160.0/codex-rs/core/src/compact.rs)保留摘要及有界的近期用户内容；该近期内容上界为 20,000 tokens。4,464 比这个保留上界还小，长用户消息下可能出现压缩后仍高于阈值的情况，不能期待每次压缩都降到小阈值以下。

当前 scope 使用 total 默认；未配置输出后压缩百分比，固定版本默认 0。没有在本轮增设另一套摘要服务或额外输出后压缩策略。既有原生回环试验证明了压缩事件及恢复链路，但使用模拟用量／摘要，不能作为真实 DeepSeek 长上下文质量证据。

## H05 当前限制为什么不匹配

当前配置实测为：累计模型预算 24,000、单次输出 4,096、最多 8 次模型请求、180 秒墙钟。代理限制单次 JSON 请求最多 1 MiB；正文最多 65,536 字符；原生上下文缓存启动前上限 64 MiB。这些都是本地产品／资源限制，与 API 的 token 窗口不同。

`api/codex_runtime.py` 当前按 `(24000-4096-2048)//4` 得到 4,464；请求前又用完整 JSON 的 UTF-8 字节数加输出 tokens 进行预留，和累计 provider usage 比较。这个保守保护把不同单位混在同一预算中。仅删除压缩覆盖后，长历史仍可能先被累计预算或字节门禁拒绝。

此外，原生压缩本身会产生模型请求及用量；它与下一次正文生成共享当前运行预算。若把压缩视为无消耗操作，也会导致压缩后无法继续。中断且没有收到 usage 的费用仍属未知，不得当成零费用或声称绝对收费上限。

## 配置基线及落地条件

来源明确的 Codex 基线如下；`model_auto_compact_token_limit` 不再由累计运行预算推导，也不强行设置成另一个自选数字：

```toml
model = "deepseek-flash"
model_provider = "deepseek"
model_context_window = 1048576
# 不生成 model_auto_compact_token_limit；使用固定内核的模型默认规则。
```

模型目录的当前 95% 可用比例与 null 默认压缩值继续保留。单次输出额度、累计用量保护、请求次数及服务时间保持独立策略；4,096 属于现役输出政策，并不在本次研究中更改为模型最大输出。

实现必须同步完成：

1. 取消累计预算到压缩阈值的耦合，统一前端窗口与阈值的分母和精度。
2. 明确 token 计量与字节保护分别负责什么；累计运行预算需容纳合法推理、原生压缩及继续生成，不能让“允许的窗口”在代理处必然失败。具体预算数值尚未验收，不在本报告中虚构推荐值。
3. 核对较大 JSON 输入、缓存、正文长度、超时及停止清理，保留身份／权限及资源保护，不能靠关闭门禁获得长窗口。
4. 配置变化会影响原生上下文重建和历史恢复；必须验收原会话继续、摘要事实保留和同任务多轮，不改写产品历史。
5. 在隔离环境验证中文长历史、跨阈值、至少两次压缩、摘要后事实与指令保留、恢复旧线程、失败重试、停止及 usage 记录。分别标明静态推导、固定原生回环和真实 DeepSeek 证据；完整窗口容量和耗时未实测前不能宣称通过。

在这些条件完成前，配置基线是待验证方案，不是已启用结果。现役配置仍为 4,464；本次没有提交、推送、部署或正式替换。
