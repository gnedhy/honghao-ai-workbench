## React 与依赖边界

- 仅增加固定开发依赖 `oxlint@1.86.0`，安装审计 0 漏洞；保留 TypeScript 7 与其余业务依赖。Oxlint MIT、Node 要求与本机 Node 24 相容，精确版本与原生平台包见锁文件。配置见 [.oxlintrc.json](../../../.oxlintrc.json)，四条规则为 Hooks 调用顺序、依赖、JSX key、重复 props；依据为 [Oxlint 官方规则](https://oxc.rs/docs/guide/usage/linter/rules/react/rules-of-hooks.html)和 [配置说明](https://oxc.rs/docs/guide/usage/linter/config)。没有引入 ESLint／新解析器；依赖图复用现有 Rolldown AST。
- 初始 51 个 TS／TSX 模块有 23 条既有 `exhaustive-deps`（含清理引用），无其余三类违规。[历史基线](../../../scripts/react-lint-baseline.json)按文件、规则、消息及整个 Hook 哈希多重计数匹配，容忍单纯移行，拒绝新增、编辑和过期条目。没有全仓自动刷新基线、关闭规则或内联禁用；旧项需在对应 Hook 修改时修复或逐项重新审查，并复验实际消费者。此基线不宣称历史问题已修复。
- [依赖清单](../../../scripts/frontend-boundaries.json)将三个工作台入口与内部实现分开；现有研发复用采购原料展示、台账纯辅助、图表纯辅助按来源／目标／符号精确登记。五个现有业务组合界面明确标注，不把整个 components 目录假定为纯控件。所有例外都有原因、维护角色、移除条件；维护角色不代表已经取得个人批准。
- [检查脚本](../../../scripts/check-frontend-quality.mjs)涵盖本地静态／动态字面量导入、再导出、类型导入和 `import()` 类型；未解析路径、计算导入、循环及纯控件直接／间接业务依赖失败。纯控件依赖路径中的 `fetch`、`XMLHttpRequest`、`WebSocket` 失败。网络别名、第三方请求库和反射尚未做数据流分析，仍需人工审查；不能将静态图通过当业务语义正确。长度与 Hook 数量仅为审查提示。
- 接入时发现 `api.ts` 的 `import('./workbenches/ProcurementNews').NewsData` 与组件 → API 构成类型循环，原样迁移新闻公开类型到既有 `src/types.ts`，保留资讯组件兼容类型导出。没有新增模块、改请求或复制展示实现。

## 实际消费者与故障验证

扩展既有 [加载脚本](../../../scripts/check-workbench-loading.mjs)，共 7 场景：采购、研发、资讯、分流加载／失败及旋转／减少动态效果；研发走势 pending／empty；销售 pending／failure／retry／empty；经 `SalesWorkbench` 挂载的实际 `SalesCalculator` 历史 pending／failure／retry／empty、计算失败及新请求先返回／旧请求晚到。所有 API 为固定合成响应，不用 setter、脱离界面的事件或源码字符串证明状态。

脚本不加载根代理，Vite 使用随机本机端口和隔离缓存，服务器 API 默认 503；所有浏览器请求核对源，外部请求、白名单外 API 请求、页面或路由错误均失败。W2 的 8 场景和普通 HTTP 编号 2 场景直接复用，总计 17 个模拟浏览器场景。它们不能证明真实数据库或权限；真实 API／事务／响应丢失与 SQL 复核继续由 `tests/test_sales_recovery.py` 的 13 个场景承担。
