# 组件复用盘点

2026-09-14 · 改造前历史盘点，保留决策依据。现役入口见 [组件索引](../../components.md)，实际完成与验证见 [组件统一验收](组件统一验收-2026-09-14.md)；下文描述当时的实现，不作为当前开发入口。

## 结论

项目已有可复用基础，不需要另建一套 UI 库。主要问题是共用组件仍寄存在业务页面、公共组件依赖业务样式，以及相同外观背后存在多份交互实现。应先整理成熟实现的归属和使用入口，再按实际使用场景统一差异。

DESIGN.md 已规定同类菜单、日期范围和表格以采购控件为设计基准；分段选择沿用白色选中底。该约定不意味着采购所有交互均已完整抽象或可无条件照搬。

| 记录筛选 | `components/RecordFilters.tsx`，采购与研发调用；已有独立 CSS | 已独立共用 | 优先直接复用；筛选值、数量由业务提供 |
| 排行翻页 | `workbenches/useMoverPaging.tsx`，采购与研发调用 | 逻辑和指示器共用，样式依赖采购 | 保留自动切换、悬停、键盘、后台页与减少动态时的暂停规则；不要重写第二套 |
| 日期范围 | `PriceDateRangeMenu` 位于采购页面，研发直接导入 | 真共用，归属不清 | 独立后适配标签和范围；不同历史口径的计算继续由业务负责 |

| 普通菜单/选择 | 研发 `Menu`、`Options`、`OwnerMenu`；组织控件有独立 `Popover`、部门选择 | 多种实现，部分需求确有差异 | 优先统一打开关闭、焦点与定位；平面单选、可搜索单选、部门树分别保留清晰用途 |
| 确认弹窗 | `DiscardChangesDialog` 位于设置页面；研发、反馈、资料、授权均调用 | 真共用，名称和归属偏窄 | 作为通用确认弹窗候选，保留主操作/危险操作、忙碌和说明区域；调用方决定是否允许取消 |
| 浏览器原生确认 | 采购价格编辑退出两处、部门分流离开一处仍用 `window.confirm` | 明确未统一 | 优先迁移到既有确认组件；离开拦截为同步事件，需验证确认后续接动作，不能只替换函数名 |
| 抽屉 | 采购 `LedgerPanel`、`PriceRecordDrawer` 等，研发 `Drawer`，另有消息抽屉 | 共用部分样式，容器与关闭逻辑独立 | 优先统一外壳及关闭入口；内容、宽度、嵌套返回和未保存拦截保留业务配置。采购部分为 div/aside，研发为原生 dialog，不能只搬 CSS |
| 展开/折叠 | 设置 `SettingsGroup` 被帮助、资料、授权记录复用；授权入口另有高度测量实现 | 部分真共用 | 先独立现有组件；紧凑入口与带描述分组可保留外观差异，统一折叠和焦点边界 |
| 开关 | 设置、授权、研发自动换算均用 `settings-mode-switch`，各自写 button | 仅样式共用 | 可统一开关控件的标签、选中、禁用和忙碌表现；授权确认、模块锁定、即时换算不能合并为同一业务行为 |
| 分段选择 | `SegmentedControl` 用于会话、知识、任务、自动化；反馈和工作台有独立标记及共用样式 | 组件与样式两条路线 | 统一前区分切换内容页与筛选条件的语义；现有组件为 tablist，不应无差别套到所有筛选 |
| 按钮 | 多页面复用全局 primary/secondary/icon CSS | 样式复用 | 不必为了包装原生 button 而新建组件；优先核对尺寸、危险态、禁用、焦点、忙碌，避免各页覆盖 |
| 数字及单位输入 | 研发收率、比例、投料共享 CSS 规则，输入节点各自存在 | 样式统一，未独立组件 | 可统一输入外观和单位布局；保留输入字符串精度，收率、比例、金额的限制由业务指定，不能统一上限或四舍五入规则 |
| 状态标签与提示 | 授权已有按状态着色标签；研发产品状态、错误及空态各自定义 | 部分成熟局部实现 | 统一视觉语义及文本换行；不能将不同业务状态合并成一个全局枚举 |
| 授权管理 | `ProcurementActivationGrants` 位于采购分流文件，以 scope 同时服务采购和研发；含确认、列表与历史 | 完整业务组合已共用 | 独立并改为中性名称即可；后续工作台需先具备服务端授权能力，不是传一个 scope 即自动获得支持 |
| 调整原因 | 采购 `ReasonSelect` / `procurementReasons`；研发 `ReasonFields` | 业务相近但实现和数据不同 | 选择+说明的表单可复用；原因目录、必填规则和保存结构由各业务提供 |
| 记录列表 | 授权 `GrantEvents/GrantHistory`、系统日志、价格记录、采购消息分别实现 | 展示模式相似，数据不同 | 可复用日期分组、事件行与加载状态；保留授权分页、价格版本、消息阅读等各自规则 |
| 组织控件 | `OrganizationControls` 提供目录、部门选择、成员字段与部门编辑 | 已有领域组件 | 继续复用；研发负责人目前为姓名选项，不可直接假定与账号 ID 等价 |
| 台账整体 | 采购与研发各有列、筛选、编辑、状态和记录逻辑 | 相似页面，不是同一业务组件 | 复用筛选、分页、列菜单、容器等局部；暂不建设万能台账或统一编辑状态机 |

路径均相对于 `src/`；组件名称可直接检索定位。当前事实来自对应实现及导入关系，不按文件名判断是否共用。

## 已确认的维护风险

1. 研发直接导入采购页面内的选择器、日期菜单及涨跌显示，同时使用采购 CSS；公共分页、排行逻辑、反馈和设置也依赖采购样式。修改采购布局时需要排查这些消费者。
2. 设置既是业务页面，又承载确认弹窗、折叠分组和滚动辅助；采购分流反向引用这些组件，设置又引用采购授权组件，存在双向模块依赖。
3. 成熟确认弹窗已被多个页面使用，但采购退出仍出现原生确认。现有组件没有形成所有同类入口必须先检查的约定。
4. 开关、输入框、标签共用样式不等于状态行为共用；单独调整页面可能再次出现禁用外观、布局与提示不一致。
5. `tests_ui` 当前六个文件主要覆盖采购 API/业务逻辑与研发分析，不是这些交互组件的完整渲染验收。源码盘点不能替代键盘、窄屏、遮挡和未保存拦截验证。

## 建议确认的统一顺序

| 顺序 | 工作 | 完成判据 |
| --- | --- | --- |
| 第一批：成熟组件归位 | 确认弹窗、折叠分组、日期/搜索选择、分页/排行、授权组件及其样式 | 消费页面从公共入口引用；不再从设置或采购页面导入通用控件；行为与已验收外观保持一致 |
| 第二批：补齐重复交互 | 原生确认替换、抽屉外壳、开关、数字输入布局、标签与分段选择 | 同类入口采用同一实现；列明并验证业务差异，不统一金额计算、权限或草稿流程 |
| 第三批：新模块接入约定 | 形成简短组件索引和选型规则，报价设计时逐项映射 | 每个拟新增控件先有现成组件适配结论；只对真实无法覆盖的需求新增组件 |

以上顺序供讨论，不构成本轮重构授权。报价与总经办 Issue 保持不变。

## 后续验证要求

- 每个被迁移组件覆盖现有消费者：采购、研发、设置、资料、帮助、反馈中实际使用该组件的入口。
- 确认弹窗验证继续编辑、确认放弃、忙碌、失败、Esc、焦点返回及嵌套弹窗；关闭不得跳过未保存检查。
- 选择器/抽屉验证鼠标与键盘、空选项、长名称、窄屏、滚动容器遮挡、锁定状态。
- 开关与授权验证选择后未提交、取消、确认成功、失败，以及禁用状态不被触发；授权以服务端为准。
- 金额和比例验证零、空字符串、无效输入、精度与单位布局，保留各业务原校验。
- 排行、分页、记录验证空数据、单页、多页、筛选复位、自动暂停与历史返回。
- 改动时运行相关测试、类型检查、隔离构建及实际浏览器回归；本次只新增盘点文档，未运行构建或业务测试。
