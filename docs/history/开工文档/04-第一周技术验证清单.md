# 第一周技术验证清单

## 1. 本周目标

不追求完整功能，先排除会推翻技术路线的风险。周末必须能证明：Windows 本地启动、Markdown 与 SQLite 一致、智能体可暂停恢复、模型接口可替换、文件访问有边界、中文路径和 UTF-8 不出错。

## 2. 已确认的本机基线

- Windows 本地开发。
- Node.js 24.15，使用 `npm.cmd`。
- npm 11.12.1。
- Python 3.12.3。
- Git 2.54.0。
- 当前不依赖 Docker、WSL、PostgreSQL。

这些信息在正式搭建时仍需通过脚本再次输出并保存验证结果。

## 3. 技术栈基线

- 前端：React + Vite + TypeScript。
- 后端：FastAPI + Pydantic。
- 数据：SQLite + FTS5，正文使用 Markdown。
- 智能体状态：LangGraph Checkpoint。
- 模型：`ModelProvider` 接口；先实现 `MockProvider` 与 `OpenAICompatibleProvider`。
- 搜索：FTS5 为主，小规模精确向量相似度为辅；V0.1 不引入向量数据库。

## 4. 验证顺序

### T1：Windows 原生启动

动作：分别启动前端与后端，完成健康检查。

通过标准：

- 一个命令启动开发环境，路径包含中文仍正常。
- 浏览器可访问；后端 `/health` 返回明确版本和数据库状态。
- 停止后无遗留进程占用端口。

### T2：Markdown / SQLite 一致性

动作：创建、修改、确认一条个人知识；删除派生索引并重建。

通过标准：

- Markdown 内容、哈希、数据库版本一致。
- 模拟失败不会留下“数据库有记录但文件不存在”的半成品。
- 重建索引后可按中文关键词找到同一条知识。

### T3：Provider 可替换

动作：同一个任务先用 Mock，再用一个真实 OpenAI 兼容接口。

通过标准：

- Workflow 和 Skill 代码不因 Provider 改变而修改。
- 密钥不进入前端、数据库、日志、错误堆栈和 Git 差异。
- 模型超时、限流、格式错误能归类并可重试。

### T4：暂停与恢复

动作：在“补充信息”和“批准 ChangeSet”两个节点强制终止进程并重启。

通过标准：

- 回到原等待节点。
- 已完成节点不重复执行。
- 已批准的写操作具备幂等保护。

### T5：受控工作目录

动作：允许读取项目样本目录，尝试读取父目录、系统目录和环境密钥。

通过标准：

- 合法路径通过；路径穿越、符号链接逃逸和目录外访问被拒绝。
- 错误日志不回显完整敏感内容。
- 写操作只能通过 ChangeSet 执行。

### T6：中文路径和 UTF-8 往返

动作：使用中文文件名、中文正文、标点、表格和长文本完成写入、检索、导出。

通过标准：

- 前端、API、SQLite、Markdown 和 Git 显示一致。
- 无乱码、截断和换行破坏。

## 5. 安全与代码审查清单

每个可提交变更至少检查：

- [ ] 变更只覆盖当前验收目标，无无关重构。
- [ ] 新增接口有 Pydantic 输入/输出校验。
- [ ] 文件路径经过规范化并验证位于受控根目录。
- [ ] 日志未包含密钥、文档正文、完整提示词或个人信息。
- [ ] 模型输出不能直接触发正式写入。
- [ ] ChangeSet 有目标版本、差异预览、风险级别和批准状态。
- [ ] 依赖版本明确，新增依赖说明必要性和许可证风险。
- [ ] 单元测试覆盖正常、拒绝、异常和恢复路径。
- [ ] 构建、测试、静态检查和差异检查全部通过。
- [ ] 提交前人工阅读完整差异。

## 6. 第一周退出条件

满足以下条件才进入完整功能开发：

1. T1 至 T6 全部通过，且每项有命令输出或测试记录。
2. 没有会迫使 V0.1 改用 Docker/PostgreSQL 的阻断问题。
3. 安全边界不是“文档约定”，而是至少有一条自动化失败测试。
4. 核心状态和恢复机制有可运行的最小样例。
5. 任务工作台视觉方案已确认并提取设计系统。
