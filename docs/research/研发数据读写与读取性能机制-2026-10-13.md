# 研发数据读写与读取性能机制

日期：2026-10-13。范围：`codex/research-data-import` 候选环境，2371 个 ERP 产品、2384 个产品成本台账条目。本文是当前代码核查与官方资料支持的设计说明；不授权正式库写入、数据库迁移或正式程序替换。

建议沿用现有 PostgreSQL 事务、冻结成本记录和版本校验，先减少重复查询、重复计算和响应体。数据准确性由确定的业务规则及版本保证，速度由按用途读取和批量读取保证；这批结构化成本数据无需增加 RAG、Redis 或新的服务架构。

## 已有机制与实际瓶颈

| 机制 | 当前实现及应保留的边界 |
| --- | --- |
| 一次读取的一致性 | `api/postgres.py::transaction` 对读请求使用 `REPEATABLE READ, READ ONLY`；同一事务内各次查询共享快照。PostgreSQL 的快照在事务内首个非事务控制语句开始时确定，其他事务之后的提交不混入本次读取。[PostgreSQL 18：事务隔离](https://www.postgresql.org/docs/18/transaction-iso.html#XACT-REPEATABLE-READ) |
| 写入的原子性 | 业务写事务持有 `pg_advisory_xact_lock`，价格／配方变更与冻结输入事件入队同事务提交。成本计算另行处理，成功时成本记录与事件 `done` 同事务提交，失败不撤销已成功的采购业务。事务级 advisory lock 随事务结束释放，但它只约束遵循相同锁协议的写入路径。[PostgreSQL 18：Advisory Locks](https://www.postgresql.org/docs/18/explicit-locking.html#ADVISORY-LOCKS) |
| 可核对的历史 | `research_events.inputs` 冻结来源；`research_cost_records` 保存成本、依赖、双取价口径及签名，`UNIQUE(event_id,product_id)` 防重复。保留现有不可变业务记录、backfill 和涨跌比较链，不用当前价格重写旧记录。签名是业务等价校验，不是访问许可。 |
| 防止覆盖其他人的编辑 | `revision`、`draft_sequence`、`simulation_token` 在保存和启用时重新校验，权限在写事务内重新读取。旧草稿或旧测算必须返回冲突，不能静默覆盖。 |
| 部门隔离 | `api/research_access.py` 从数据库读取当前账号状态、研发等级和部门归属；跨部门投料允许取成本，但隐藏对方配方图。摘要、详情、历史、导出和后续缓存均需保持这一规则。 |

优化前，`_rows` 对每个产品调用 `linked_history`，后者查询 backfill 和正式历史各一次；`version_history` 也逐产品读取历史。这是查询次数随产品数量增长的 N+1。列表会先读取并解析大 payload，再删去图和计算字段；详情曾读取大量无关产品，并重新核算完整图。原前端 `researchData.ts` 同时请求 products、history、formulas，每 10 秒重复这一组合。本轮已改为同一只读事务的 overview，批量历史在请求内复用，先限定当前授权产品，再在 SQL 中去掉摘要不需要的大字段；不使用跨账号或跨请求的全局缓存。

隔离环境实测来自 `read-acceptance.json`：F-182G 详情原为 **4.578／7.804 秒、2,039,453 字节**，最终样本为 **1.2081 秒、206,235 字节**；历史版本先取摘要，从完整 37,545,322 字节缩到 **772,225 字节、1.0391 秒**，单产品冻结明细为 **39,728 字节、0.1635 秒**。研发三部整个 overview 包含 969 个产品的台账、历史和配方目录，三次样本为 2.3572／2.4615／2.5435 秒；全部部门 2384 个产品汇总为 4.6557 秒。三个并发读取者的六次样本最大 4.7966 秒，成本与部门范围均一致。这些是本机隔离环境的小样本，包含同时运行回归时的负载，不能当作 P95 或所有产品的性能保证。

正式库已有 239 条成本记录、1386 条历史回算记录，已逐行核实完整保留在隔离库。研发三部 969 个新产品仅有本次导入的一期；研发五部已有产品保留多期。单期提示不能用虚构历史或自动回算新 ERP 配方来消除。


## 本轮已实现的直接优化

这些优化限于候选程序及隔离验收，不改变来源数据、成本规则或正式数据。

1. **单产品读取**：详情只取目标产品及核算所需依赖，不先生成整个产品台账。更新中或失败时继续读取已完成冻结记录；正常状态的实时取价仍复用现有完整图计算，未在本轮改为裁剪依赖闭包，避免改变浓度、回收及库存兜底规则。单产品依赖闭包求值可作为下一步独立优化。不能为了提速把“当前取价”和“已发布历史成本”混为一个值。
2. **批量历史读取**：一次读取有权查看的产品历史，在请求内按产品归组，复用既有比较算法；两次批量查询代替每个产品各查询两次。采购期识别、两位成本涨跌比较、缺价断链及 backfill 语义保留，并对单产品和批量结果做逐字段验证。摘要查询在 SQL 层只返回必要字段，避免传回完整图再删除；返回给浏览器前仍执行权限投影。
3. **缩小页面用途**：台账主要展示内编、部门、负责人、双成本、状态、变化及版本。本轮摘要去除配方图、重复计算与来源哈希；当前台账和配方目录仍保留 lines 数组以兼容已有读取，未把它们改成只有条数的更薄响应。完整冻结图按点击读取。历史首屏只取版本摘要，选中版本仍先取产品清单，点击产品后再取该事件的单产品冻结明细。沿用 history/{id} 路径的 summary 与 product_id 参数，默认完整返回保持兼容；参数不扩大权限范围。材料候选由详情按需读取；进一步精简台账与目录的细行，需同步既有消费者并单独验证。
4. **读取状态不干扰使用**：首次加载与后台刷新区分；后台刷新保留上次成功数据，显示刷新失败，不反复清空表格。复用 AbortController、防重入和平台原生 15 秒超时；初次失败暂停自动轮询，保留错误供手动重试；切页／连续点击取消旧响应，旧响应不能覆盖新产品。退出与换账号沿宿主卸载处理；读取收到 401／403 时清除旧台账、目录和详情，不能继续显示已拒绝的数据。
5. **只格式化显示**：数据库与计算继续用 Decimal／十进制字符串，价格、数量及比例默认显示两位小数，悬停读取原始完整值；缺失显示缺失，不能变成 0。取价依据显示四字标签及可聚焦的说明 icon，悬停显示完整依据，键盘可聚焦并由无障碍名称提供完整说明。编辑和导出不能把显示舍入值写回计算输入。PostgreSQL `numeric` 与浮点数的精度性质不同；若未来将文本金额迁入数值列，应选择合适 `numeric`，不得改用浮点列。[PostgreSQL 18：数值类型](https://www.postgresql.org/docs/18/datatype-numeric.html)

## 多次请求的一致性与后续读取契约

**同一事务一致，不等于所有后续点击永远是同一版本。** 原 `Promise.all` 的三个请求各自开事务，可能分别看到变更前后；原 overview 也分开读取。本轮 overview 已增加外层只读事务并复用内部查询，前端一次接收整套结果；并发目录更新的回归验证了台账与目录仍在同一快照。冻结历史的按需读取绑定 event_id；普通实时产品详情仍按当前状态读取，后续分页与列表到实时详情的完整版本协议尚未实现。无需把事务跨用户操作保留。Psycopg 的显式 transaction context 正常退出提交，异常回滚；嵌套上下文使用保存点，适合复用已有事务入口。[Psycopg：事务上下文](https://www.psycopg.org/psycopg3/docs/basic/transactions.html#transaction-contexts)

若再拆成服务端分页和按需详情，响应应携带明确的业务版本。建议区分：①已完成成本发布版本及对应冻结事件；②目录／草稿／待计算状态；③当前授权范围。用户点开详情时带列表的期望版本；服务端能从冻结记录重现就返回该版本，否则提示版本已更新并重新加载。分页也绑定相同版本，防止跨页重复或漏项。不能只用 `MAX(cost_record.sequence)` 当全部数据版本：没有新成本记录时，负责人、停用、草稿、pending 状态或权限仍可能改变；数据库序列也不是事务提交顺序证明。

列表分页必须在授权、筛选、排序后执行，并返回同版本的总数；采用含唯一键的稳定顺序。后期大历史用 `(时间, id)` 游标，避免大量 OFFSET。统计和部门汇总不能只基于当前页；导出继续覆盖账号全部获准产品，不受页面分页影响。[PostgreSQL 18：LIMIT 与 OFFSET](https://www.postgresql.org/docs/18/queries-limit.html)

**版本未变再少取，不先缓存后鉴权。** 后续可用 ETag／If-None-Match，让未变化的 GET 返回 304，客户端复用同账号、同范围、同查询条件的既有结果。判断前必须重新确认会话、账号启用状态、部门范围及操作权限；正常检查会返回拒绝时，不能因为 ETag 一致返回 304。这符合 HTTP 预条件在正常请求检查后评估的规则。[RFC 9110 §13.2.1](https://www.rfc-editor.org/rfc/rfc9110.html#section-13.2.1)、[MDN：If-None-Match](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/If-None-Match)

ETag 要反映实际授权表示及查询参数，不能把管理员响应按 URL 缓存给普通部门。优先页面内短期复用；若明确启用浏览器条件缓存，用 `Cache-Control: private, no-cache`，并处理账号切换清理。现有标记 `no-store` 的材料、导出不在本轮擅自改动。`private` 限制共享缓存，`no-cache` 要求复用前验证；它们本身不替代权限检查。[MDN：Cache-Control](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Cache-Control)

仅把完整响应算完再 hash 虽能省传输，仍不能省 SQL／解析／计算。若后续测量确认有必要，应在所有相关写入、事件完成／失败与授权修改路径中维护事务内业务版本，再先读轻量版本决定是否生成响应。它涉及完整写入覆盖和潜在迁移，需要单独实现与兼容验收；本轮没有新增版本表。

## 失败、导出及性能证据

当前连接上限保护为连接 5 秒、单 SQL 30 秒、锁等待 10 秒、事务闲置 60 秒；前端研发交互读取 15 秒超时；导出及写入未套用该期限。这些阈值不是响应性能目标。`statement_timeout` 限制单条语句，不限制一个请求中数千条查询或 Python 计算；前端取消也不自动证明服务端 SQL／CPU 工作已终止。[PostgreSQL 18：客户端默认配置](https://www.postgresql.org/docs/18/runtime-config-client.html)

读取失败保留明确标为旧的成功结果及重试入口，不能一直转圈、显示半套新旧数据或把失败当空列表。初次请求失败无旧值时显示错误。写入失败由事务回滚；响应丢失时先查询 revision／事件状态再重试，不能盲目重复启用。事件失败仍呈现 `failed`，不能把旧成本标作新版本已完成。只对可重试的瞬时数据库错误做有界整事务重试，不重试业务冲突或未授权。

当前 `export_costs` 在一个只读事务内取产品和冻结成本，关闭事务后生成 xlsx，这个边界应保留。将其中逐产品成本查询合成批量读取即可减小调用量；不能边导出边取不同版本，也不能通过取消权限过滤提速。若未来需要长导出，先冻结导出版本及范围，再异步生成，不能长时间保持用户交互事务。

应分别记录 SQL 次数／时间、JSON 解析及成本计算时间、响应字节、浏览器渲染耗时；在隔离库对 SELECT 使用 `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)`，保留优化前后计划。ANALYZE 会实际执行语句；不要用于未授权的正式写语句。现有 `(product_id,sequence)`、backfill 主键和版本唯一约束先复用；只有计划证明扫描／排序成为瓶颈才加索引。数据库计划不含全部文本转换及网络耗时，故 SQL 快不代表页面快。[PostgreSQL 18：EXPLAIN](https://www.postgresql.org/docs/18/using-explain.html)

验证至少覆盖同数据版本新旧成本／收率／缺价／依据逐字段一致、跨部门泄漏、撤销权限后的详情及 304、并发草稿冲突、事件更新中的列表／详情／导出一致性、超时取消与连续点击。以当前 2384 条和现有账号先测冷／热读及小规模并发，报告中位数、P95、响应字节和错误数。**详情约 1 秒内、摘要约 1 秒内可作候选目标，尚未证明 P95 或所有产品均达标**，不得用几个成功样本替代完整验收。

## 不引入的机制与发布边界

普通同步 FastAPI 路由已在线程池执行；改成 `async def` 不能消除 N+1 或重复计算，直接在 async 路由里调用阻塞数据库代码反而会阻塞事件循环。[FastAPI：同步与异步路径函数](https://fastapi.tiangolo.com/async/#path-operation-functions) 连接池只在测量显示建连／排队明显时考虑，并明确容量、获取超时、故障恢复与服务租约连接；它不会减少每次请求查询量。[Psycopg：连接池](https://www.psycopg.org/psycopg3/docs/advanced/pool.html) 本轮不新增连接池、Redis、读副本、多 worker 或更短轮询。

RAG 原始方案服务于检索支撑的语言生成，其检索记忆是文档向量索引。[RAG 原始论文](https://arxiv.org/abs/2005.11401) 对本项目的推论是：产品内编、BOM 引用、库存取价、收率平均、金额及权限应继续由 SQL、事务和确定性规则处理。将来查询研发报告／制度等非结构化材料可以另做带来源的检索问答，但不能据向量相似度推定替代料、负责人或正式成本，也不能由生成答案绕过写入确认。本轮不增加 AI 层。

上述直接优化可在现有候选范围内完成；服务端分页、跨请求版本协议及索引／版本表等后续项须与现有消费者、销售读取、导出和 Harness 分支的迁移顺序一并核对。正式替换仍须当前版本验收、备份恢复及用户授权，不能直接把带测试账号的隔离库复制到生产。

本轮在隔离库保留 summary-query-plan.json 的 SELECT 执行计划及三个并发读取者的小规模样本；未进行大规模并发压力或正式服务测量。后续分页、条件缓存和跨请求业务版本协议尚未实现。未授权正式写入或发布，现役环境不因本说明而改变。
