# 工作台性能预算

新增模块、扩充台账、改变读取或计算流程时，先按本页确认固定负载与预算，再执行统一验收。预算的唯一数值来源为 [performance-budgets.json](../../scripts/performance-budgets.json)，本页维护测量含义与变更流程。

## 测量范围

| 检查 | 固定负载与统计 | 完成条件 |
| --- | --- | --- |
| 正式构建体积 | Vite manifest 的首页静态依赖、全部输出 JS/CSS、各已实现模块扣除首页依赖后的增量 JS；gzip level 9，KiB = 1024 字节 | 全部预算都有测量；静态依赖去重，额外 worker 等输出计入总量；模块保持 lazy，且不进入首页静态依赖 |
| 实际组件浏览器 | 正式构建的采购台账 2,000 行、研发 500 行、销售选择器 2,000 产品／4,000 成本选项；1440×1000，Chromium CPU 降速 4 倍，每模块 5 个新 context | 页面和数据结果正确，采购／研发真实翻到第 2 页再筛选，销售可选择目标；就绪、筛选、分页的中位数与最大值及 API 请求数都在预算内，console／页面错误及意外请求为零 |
| PostgreSQL 业务读取、计算与导出 | 专用 test 库：2,000 原料及正式价格／库存、200 配方各 12 行投料、每产品 20 条历史；采购 overview、研发 listing、销售目录、12 面板测算、成本 Excel 导出、真实成本事件处理，各 9 次 | 每次核对真实结果；导出核对总览数量／成本和负责人明细，重算实际新增 200 条成本并保持原历史指纹；业务层耗时和 SQL 调用数逐项符合预算 |

浏览器 fixture 使用实际组件和样式，GET 返回合成固定数据；后端性能用例执行真实 Store 与 PostgreSQL。两种测量分开解释：浏览器数值不含真实 API／广域网时延，后端数值不含 HTTP、认证和浏览器渲染。首个 Store 调用及其后各次调用全部保留，不丢掉最慢样本；数据库缓存未清空。

重算测量 `ResearchStore.process_events`，包含双口径计算及冻结记录写入；每次在测试库恢复相同的 4,000 条原历史，并准备同一 24→25 的价格变化事件，确保每次实际计算、写入 200 条，而不是测空队列或成本未变化的短路。事件准备、历史核对及工作簿解析在计时外；原历史内容每次重新比对。该测试 fixture 的研发处于 prototype，不启动第二个后台研究 worker；整个测试仍持独占测试库锁。

浏览器就绪从导航的 `performance.now()` 起算，到预期 DOM 加上两次 animation frame；筛选从实际 input 事件、分页从实际 click 事件起算，到预期结果及两帧。此指标是实验室回归预算，不称为生产 LCP／INP 或完整 App 登录体验。CPU 降速相对于运行机器，不能等同于某款真实移动设备；方法参见 [Chrome 性能参考](https://developer.chrome.com/docs/devtools/performance/reference/)、[Vite manifest](https://vite.dev/config/build-options)及 [Playwright CDP](https://playwright.dev/docs/api/class-cdpsession)。

初始构建预算按当前实测体积留约 12%–29% 空间；浏览器与 Store 耗时留出共享 runner 波动空间，同时保护最大值。请求及 SQL 调用数按固定样本实测冻结。当前研发和销售读取含逐产品查询，SQL 数量随产品规模增长；本次预算防止固定负载退化，不证明任意规模下查询成本恒定，也没有完成这部分批量查询优化。

## 开发与验收

`npm run verify -- --scope frontend` 执行构建、浏览器性能和完整性检查；`npm run verify` 另外执行专用数据库性能用例与结果核对。采购、研发、销售定向范围同样包括该性能用例。已有 CI 的 `frontend`、`full` 调用统一 verifier，因此预算超限会使对应必需检查失败；工作流修改随源码合并生效，远端是否通过以实际 Actions 为准。

统一验收开始测量前清除旧性能 JSON，并重新构建、采样；结尾核对全部指标、负载、profile、样本数量与中位数／最大值。单独运行结果检查只核对现有收据，不能代替一次新的统一验收。输出位于 `.scratch/performance-budget/`；CI 只上传白名单中的数值、合成负载维度和调用数。`within_limits` 仅表示该数值报告是否超限，整体通过以 job 和实际 API 执行收据为准；不上传 SQL、参数、凭据、业务响应、原始错误正文或数据库。

超限时保留原报告，定位体积、渲染或查询变化并修复，再验证受影响范围。不得缩小负载、删除慢样本、漏掉模块或把失败记作通过。门禁负例保护超限、漏测、非有限值、样本不足、模块提前加载、伪造统计及无本次记录的放宽。

## 模块扩展与预算变更

新增已实现工作台时，同步 [静态接入](workbench-integration.md)、性能策略、实际 fixture 与 [回归清单](../../scripts/regression-contract.json)。必须有该模块的增量构建预算、五项基本浏览器指标，分页模块另在 paginationModules 登记分页预算，以及至少一个 `apiProfiles` 条目，指向被收集且在该模块 `apiPatterns` 范围内的真实性能用例；新浏览器场景和后端操作须实际产生该模块的全部样本。新增指标没有实测收据会失败。增加新模块负载维度可用正整数；原负载维度与原 API profile 保持不变，替换测量协议另作明确设计与审查。

已有预算可以收紧；删除预算直接失败。确需提高上限时，在本次 diff 中新增或更新 `docs/performance/budget-revisions/<事项>.json`：

```json
{
  "schema": 1,
  "revisions": [
    {
      "metric": "bundle.totalJsKiB",
      "from": 380,
      "to": 390,
      "reason": "说明本次已批准功能为什么增加成本，以及已做的优化取舍。",
      "evidence": "填写本次基线与候选的实际报告路径、固定负载结果及审查结论。"
    }
  ]
}
```

示例不是批准。自动检查只验证同一指标、旧值、新值与足够明确的文字记录出现在本次变更中；需求和规范审查必须判断证据是否真实、优化是否充分及新上限是否合理。逐条比较上述五个字段；旧记录未在本次变化不能作为放宽依据，改文件空白或其他条目不能复用旧证据。首次引入仅允许固定基线 `ea611e42b85b68ee7e2543849cdda73e842f4e63` 缺少旧策略，其他基线缺失一律失败。

生产观察、真实用户指标及持续巡检属于后续工作；本页的隔离预算不批准任何正式部署或业务写入。

## 开发效率

开发阶段沿用定向 verifier，前端范围提供约一分钟的反馈；集成与发布仍执行完整范围。CI 保留 frontend 15 分钟、full 60 分钟的超时边界，超时按失败处理。统一 verifier 逐阶段记录耗时；完整 JUnit 可按文件及测试聚合耗时，定位准备、真实接口／事务、恢复和浏览器成本。用例耗时包含 fixture 准备与清理，不能直接解释为某个业务接口延迟。

2026-10-04 本机完整基线为 501 API、66 Node、17 模拟、95 实库场景，总计约 28 分 36 秒，其中 API 阶段约 27 分 44 秒；五个实库浏览器包装合计约 6 分 20 秒。前端范围约 54 秒。保留本次分阶段与 JUnit 耗时证据，再选择实际瓶颈优化；不靠缩减回归或并行重置同一个数据库提速。本轮产品代码及既有业务用例未改，后续完整流水线另受新增性能负载影响。
